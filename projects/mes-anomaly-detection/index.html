01 · Overview

반복 대조 작업을
탐지 체계로 전환했습니다.

기존 업무의 불편함을 줄이는 데서 멈추지 않고, 데이터의 정상 상태를 정의하고 이상 발생 근거를 남기는 시스템으로 확장했습니다.

Problem

여러 화면과 Excel을 사람이 직접 대조

담당자가 생산실적, 태그 데이터, QR 정보를 각각 조회한 뒤 Excel과 비교해야 했습니다. 조회 기간과 라인이 늘어날수록 반복 작업이 많아졌고, 입력 누락이나 판단 오류를 놓칠 가능성도 커졌습니다.

Core Challenge

서로 다른 데이터가 같은 작업을 의미하는지 판단

각 화면은 식별자와 시간 표현 방식이 달랐습니다. 단순히 값 하나를 비교하는 방식으로는 정상 지연과 실제 누락을 구분하기 어려워 라인, 품목, 작업 시간, QR, 태그 상태를 함께 고려하는 매칭 기준이 필요했습니다.

Solution

수집 → 정규화 → 상관분석 → 탐지 → 기록

데이터 수집 방식을 탐지 로직과 분리하고, 공통 데이터 모델로 정규화한 뒤 규칙 기반 탐지 엔진에서 이상 여부를 판정하도록 구성했습니다. 판정 결과와 수집 과정을 로그로 남겨 현장에서 근거를 확인할 수 있게 했습니다.

02 · Architecture

MES 핵심 시스템을 건드리지 않는
독립적인 탐지 계층

운영 중인 생산관리 시스템의 위험 범위를 최소화하기 위해 읽기 중심의 별도 수집·분석 계층으로 구성했습니다.

02
DATA SOURCESMES · Tag · QR

생산실적, 태그 현재값, QR 및 품목 정보를 조회합니다.

COLLECTIONAPI First + Playwright

API를 우선 사용하고 불가능한 화면은 브라우저 자동화로 보완합니다.

DETECTIONNormalize · Match · Judge

공통 모델로 정규화한 후 시간·라인·품목 기준으로 상관분석합니다.

OUTPUTReact · Excel · Logs

이상 항목, 판정 근거, 실행 상태와 보고서를 제공합니다.

구현 범위에 대한 기술적 설명

현재 버전은 API 조회와 Playwright 화면 조회를 조합한 주기적 수집 방식입니다. 프로젝트 명칭은 현장의 즉시 확인 목적을 반영해 “실시간 자동탐지 시스템”으로 사용하지만, 이벤트 스트리밍 관점에서는 준실시간 구조이며 향후 서버 이벤트 또는 메시지 기반 수집으로 확장할 수 있도록 데이터 소스와 탐지 로직을 분리했습니다.

03 · Key Decisions

기능보다 운영 안정성과
추적 가능성을 먼저 고려했습니다.

03
01

API 우선, Playwright fallback

가능한 데이터는 API로 수집하고, API 접근이 어려운 화면은 Playwright 기반 조회로 보완했습니다.

Why this way?

화면 자동화에만 의존하면 UI 변경과 브라우저 상태에 취약합니다. 반대로 API만 고집하면 실제 업무 화면의 일부 데이터를 놓칠 수 있어 두 방식을 하나의 데이터 소스 인터페이스로 묶었습니다.

02

수집과 탐지 로직 분리

MES 화면 구조가 바뀌더라도 이상 판정 규칙 전체를 다시 작성하지 않도록 수집 계층과 탐지 계층을 분리했습니다.

Why this way?

데이터 취득 방식은 자주 바뀔 수 있지만 정상·비정상 기준은 업무 규칙에 가깝습니다. 변경 주기가 다른 책임을 분리해 유지보수 범위를 줄였습니다.

03

판정 근거가 남는 규칙 기반 탐지

초기 단계에서는 설명하기 어려운 모델보다 현장 담당자가 검증할 수 있는 명시적 규칙을 사용했습니다.

Why this way?

이상 항목이 표시됐을 때 “왜 이상인지” 설명할 수 있어야 오탐을 조정하고 실제 업무에 적용할 수 있습니다. 라인·품목·시간·QR 상태를 근거로 남기도록 구성했습니다.

04

단계별 운영 로그

로그인, 화면 이동, 조회 조건, 수집 건수, 비교 결과, 저장과 오류를 단계별로 기록했습니다.

Why this way?

현장 시스템에서는 실제 데이터 이상과 수집 실패를 구분해야 합니다. 전체 실행 흐름을 남겨 재현과 원인 분석이 가능하도록 했습니다.

05

BFF 기반 UI 연결

React 화면이 MES 구조에 직접 의존하지 않도록 FastAPI BFF가 작업 실행, 진행 상태, 취소와 결과 조회를 담당하게 했습니다.

Why this way?

프론트엔드에서 자동화 세부 동작을 알 필요가 없고, 기존 Tkinter와 기존 API 경로도 유지할 수 있어 단계적인 전환이 가능했습니다.

06

기존 업무를 멈추지 않는 구조

MES 저장 로직과 DB 스키마를 직접 변경하지 않고 별도 시스템에서 데이터를 읽고 분석했습니다.

Why this way?

생산 시스템의 장애 영향도를 낮추고, 탐지 시스템에 문제가 생겨도 기존 업무가 계속될 수 있도록 실패 범위를 격리했습니다.

04 · Detection Rules

현장에서 확인 가능한
이상 유형으로 분류했습니다.

아래 항목은 실제 구현 범위와 확장 가능한 탐지 기준을 구분해 표현했습니다.

04
01

입력 누락

생산실적에는 존재하지만 대응하는 태그 또는 QR 정보가 없을 때 확인 대상으로 분류합니다.

02

데이터 불일치

라인, 품목, 작업 시간 또는 수량 정보가 허용 범위를 벗어나 서로 일치하지 않는 경우를 탐지합니다.

03

수치 이상

태그 현재값, 투입량, 생산량 등 비교 대상 수치의 차이가 업무 기준을 초과하는 경우를 표시합니다.

04

QR·태그 이상

QR 또는 태그 식별 정보가 예상 작업과 연결되지 않거나 중복·재사용이 의심되는 패턴을 확인합니다.

05

수집 오류

로그인 실패, 화면 로딩 실패, 빈 테이블, 예상 헤더 누락 등을 실제 생산 이상과 분리해 기록합니다.

06

예외 상태

정상적인 작업 지연, 재작업, 데이터 반영 지연을 오탐으로 처리하지 않도록 예외 조건을 조정합니다.

07 · What I Learned

코딩보다 어려웠던 것은
정상과 비정상을 정의하는 일이었습니다.

Domain Understanding

현장 데이터의 의미를 알아야 탐지할 수 있다

같은 숫자라도 작업 시점, 라인, 품목, 재작업 여부에 따라 의미가 달랐습니다. 데이터 구조뿐 아니라 실제 생산 흐름을 이해해야 탐지 규칙을 설계할 수 있었습니다.

Detection Engineering

오탐과 미탐 사이의 기준 조정

모든 불일치를 오류로 처리하면 현장에서 사용할 수 없습니다. 정상 지연과 예외 상태를 반영하고 판정 근거를 설명 가능하게 만드는 과정이 중요했습니다.

Operational Reliability

성공 경로보다 실패 경로를 먼저 본다

로그인 실패, UI 변경, 빈 데이터, Excel 갱신 순서처럼 운영 환경에서 발생하는 실패를 분리해 기록하고 재시도 또는 중단 기준을 설계했습니다.

Security Perspective

제조 데이터 흐름은 보안 탐지와도 닮아 있다

여러 로그를 수집하고 상관분석해 정상 행위에서 벗어난 패턴을 찾는 과정은 보안 이상행위 탐지와 구조적으로 유사합니다. 이 경험을 OT·스마트팩토리 보안 역량으로 확장하고 있습니다.
