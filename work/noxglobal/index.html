Performance

Production performance

Cut average API latency from ~400 ms to 95 ms (~76%) and daily average CPU from 57% to 30%.

What I did
  • Query tuning: resolved N+1 queries and narrowed query scope
  • Reused DB connections (persistent connections), removing per-request connection setup cost
  • Applied Django's cached template loader, cutting template rendering time by up to 86%
  • Converted synchronous queries to asynchronous processing, minimizing perceived latency
  • Tuned FastCGI worker recycling and served static files directly from IIS, reducing worker load
Incident Response

Gateway incident root cause

Screens repeatedly froze for about 20 seconds and then failed in the early morning. Correlating logs across layers traced the failure to the network gateway, not the server or the switch.

Problem
Worker backlog and failed response delivery were mixed together during the incident, so IIS logs alone could not tell a server-side cause from a network-side one.
What I did
  • Matched the same requests 1:1 across the front proxy and application IIS logs
  • 12 of 15 slow requests finished in the app within 1 s while the proxy took over 5 s (one: 0.03 s vs ~19 s), with connection-abort, transmit-timeout and peer-reset errors
  • Added a connection log recording MES · ERP · SCM reachability every 2 seconds
Result
SCM traffic, which shares the switch but bypasses the gateway, stayed healthy during later incidents, ruling out the switch and pinpointing the gateway.
MonitoringRequest Tracing

Per-request diagnostics

Split each request's processing time across MES DB, external DBs and the application to pinpoint bottlenecks and worker saturation.

Problem
MES runs on a few single-request workers. When ERP or SCM slowed down, waiting workers piled up and unrelated MES requests stalled too, but nothing showed which request held a worker or where its time went. Requests that hung or died were never logged at all.
What I did
  • Django middleware + DB hooks bucketed query time per database; the rest is application time
  • Logged only requests over a threshold, per process, to files rather than the busy DB
  • A watch thread recorded in-flight requests past 5 s once, with the code location they were stuck at
Result
Slow and stalled requests, and which requests occupied workers at that moment, became visible in the server-status tab, making dependency bottlenecks and worker saturation traceable.
